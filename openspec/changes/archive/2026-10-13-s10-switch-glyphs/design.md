# Design

## Context

See `proposal.md` - Why. The current state: `controller_geometry.json`
annotates S10 S-cells (`S1.1`/`S1.2` → `"kind": "rotary"`, S1.3–S1.10 →
`"small"`) and M4 B-cells (`"touch"`), generated by
`tools/acquire_geometry.py`. `ElementCellEntry` (`src/physical.rs:97-116`)
has `col/row/x/y/w/h/label/dir` — no `kind` — so the annotation is dropped
at deserialization (no `deny_unknown_fields`). `preprocess_cells` (404-433)
builds `ElementCell` without it. `cell_visuals` (`src/gui/physical.rs:1166`)
matches `ComponentKind::Switch` to one glyph set (`▣` ON / `□` OFF, plus
`◉`+percentage for `Value`). Three call sites pass `(comp, flag, fader)`.

## Goals / Non-Goals

**Goals:**

- Rotary vs toggle distinguishable at a glance on the S10 faceplate.
- Everything else pixel-identical.

**Non-Goals:** everything in the proposal's Non-goals.

## Decisions

### D1 — `kind: Option<String>` on entry and cell, carried in `preprocess_cells`

Both structs gain `#[serde(default)] pub kind: Option<String>` (entry) and
plain `pub kind: Option<String>` (cell, cloned through). Absent → `None`
→ today's path, so controllers without annotations (and any stale data)
render unchanged.

*Why:* the annotation is faceplate data that already ships in the JSON;
reading it is strictly additive. Keeping it geometry-side (off
`HwComponent`) respects the patch-data vs faceplate-data split — components
are what the patch declares, kinds are what the panel is.

### D2 — Branch the Switch arm on the geometry kind

`cell_visuals` resolves the switch glyph from the cell kind passed by the
spec site: `"rotary"` → round set (`◉` ON / `○` OFF, `◉`+percentage for
`Value`), anything else (including `None`) → the existing toggle set. The
kind reaches the arm as a new `switch_kind: Option<&str>` parameter
(defaulting `None` at the label-helper and test call sites).

*Why:* round-vs-square mirrors the physical panel (round rotary knobs vs
rectangular toggles) and reuses glyphs already in the table — no new
drawing language. The `○` idle glyph is shared with buttons/LEDs, but face
context (S10 switch cell + label) disambiguates, exactly as `◉` is already
shared between knobs and encoders.

*Alternatives:* new `ComponentKind` variants (RotarySwitch/TouchSwitch —
exhaustive-match churn across handler/graph/paint for a rendering-only
distinction); resolving kind inside `cell_visuals` from global geometry
(pure painter reaching into loader state — wrong direction).

### D3 — Spec site resolves kind via the module's cells

At the spec call site the component's geometry cell is in scope (the same
lookup that yields the rect); pass its `kind`. Unaddressed cells never reach
the arm (dimmed branch). The label helper keeps `None` (detached text
context, same reasoning as the shift D1 call).

### D4 — M4 `touch` rides along untouched

The field carries `"touch"` through with no consumer yet; the fold rule
keeps covering touch plates. No behaviour change, no dead code claim — it
is loaded data with a documented future consumer (parity work, bead
`droid_tui-y57` territory).

## Risks / Trade-offs

- [`◉` already means knob/encoder] → shared glyphs are established practice
  in this table; the S10 switch cell + label + faceplate disambiguate, and
  the shape contrast (round vs square) is the actual signal.
- [Old JSON without `kind`] → `None` → toggle set: identical rendering, so
  regeneration is never forced.
- [Screenshot churn] → only S10 faces change glyphs; all other shots must
  stay byte-identical (the re-bless proves it).
