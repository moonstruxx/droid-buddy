# Design

## Context

See `proposal.md` — Why. The constraints that shape the approach:

- `RackSpec` (`src/physical.rs`) already models `[physical.rack]`: `rows: Vec<RackRow { he, hp, label }>`, `top_mount_te`, `side_mount_te`, and `assign: HashMap<String, usize>` keyed by the module key `"{controller} {instance}"` (`PhysicalModule::key`, e.g. `"P2B8 1"`; the master is the bare `"CV I/O"`). `RackLayout::pack` fills rows left-to-right in chain order and honours `assign` as a per-module override. There is no module inventory today: a module exists only because `patch.hw_components` contains one of its components.
- `PhysicalLayout::build(&Patch, MasterModel)` pushes the master faceplate at position 0 and then walks `patch.hw_components`, grouping by `(controller, module_instance())`. `App::master_model()` answers `MasterModel::Master` when no plan is stored, so a master faceplate is resolvable without a patch.
- `gui::physical::physical_spec(app, pane)` starts with `let patch = app.patch.as_ref()?`, builds the chain and rack, and publishes `component_rects` from the drawn cells. `App::physical_chain_and_rack()` (private) has the same `?` and backs both fits, so neither fit runs without a patch.
- `rack_geometry` (`src/gui/physical.rs`) emits unaddressed cells for every module **except** the master (`module.controller != "CV I/O"`), a deliberate choice that kept a bare patch's master front byte-identical.
- Element identity is label-derived only: `preprocess_cells` calls `label_element(c.label)`, which needs a digit after the family letter (`B1.3` → 3, `I5` → 5). `Gin1`/`Gout1`/`serial in`/`USB`/`SD reload` yield `None`, and `unaddressed_cells` skips cells without an element. `cell_for` then falls back to the positional `cells.get(element - 1)`, which is why `I1` resolves to `O1` on MASTER18.
- `controller_geometry.json` is generated by `tools/acquire_geometry.py`, whose `--check` verifies the file against the generator (per-family `token_counts` match `addressable` cell counts, grids conform, labels are unique per family). A hand edit of the JSON alone fails the check.

## Goals / Non-Goals

**Goals:**

- One configured inventory decides which modules the rack view shows and in which rows, independent of the loaded patch.
- The module UI paints with or without a patch; with no inventory, rendering is byte-identical to today.
- Every declared element of an inventoried I/O module renders, including MASTER18's gate column and the expanders' serial jacks.
- Element identity stops being a label-parsing side effect: a cell either has an identity or it does not render.

**Non-Goals:**

- No hardware probing, no discovery, no inference from anything but config and patch.
- No interaction on unaddressed cells (hit rects, hover reveal, selection, label editor, modifier wash).
- No E4 ring redesign, no change to fold rules or LED colouring.
- No migration of `assign`, no automatic generation of the inventory from a patch.

## Decisions

### D1 — The inventory lives on the row, not as a flat chain list

`RackRow` gains `modules: Vec<String>` (`#[serde(default)]`), and each entry is a module key. Rejected alternatives: a flat `[physical.rack] modules = [...]` list keeps chain order but must re-introduce row placement through `assign`, which is exactly the indirection the physical rows already express; and deriving an inventory from the patch's declared sections cannot show a module the patch never mentions, which is the request.

Consequence: `assign` keeps its meaning for modules the inventory does not list, and the two never fight — a listed module ignores `assign`.

### D2 — The chain is inventory ∪ patch, patch-only modules appended

`PhysicalLayout::build` orders inventory modules first (row order, then list order) and appends every patch module the inventory does not name, in patch declaration order. A forgotten inventory entry must never hide hardware a patch addresses; the inverse — an extra dim faceplate — is visible and harmless. Rejected: inventory-authoritative (a typo silently drops a patched controller).

### D3 — `build` takes `Option<&Patch>` and records that the chain is inventory-driven

The chain builder accepts a missing patch instead of `App` synthesising an empty one: a fake `Patch` in `App.patch` would leak into the load status, the label store key, the master plan and every "is a patch loaded" branch. The build result carries `inventory_driven: bool` (true when at least one row lists modules), which is the single switch the painter reads. When `inventory_driven` is false the builder reproduces today's chain exactly, so the switch cannot silently change an existing setup.

### D4 — Unaddressed emission is switched by the chain flag, not by the controller name

`rack_geometry` currently suppresses the master's unused cells by name. It becomes: suppress only when `!chain.inventory_driven`, in one place, so the emission rule has one owner and the patch-derived path stays byte-identical. `component_rects` still excludes unaddressed cells (they have no `component_index`), and with no patch the published list is empty.

### D5 — Element identity becomes data, with the label as a fallback

`ElementCellEntry` gains `#[serde(default)] element: Option<u32>` and `kind_letter: Option<char>`; `preprocess_cells` prefers them and falls back to `label_element`. MASTER18's gate cells are renamed to the patch vocabulary (`I1`, `I2`, `G1..G4`) rather than given bare numbers, because those names *are* the tokens a patch uses and the rename fixes `cell_for` at the same time. The R2M/R2C jacks get explicit numbers with no kind letter and stay `addressable: false`, because no patch token reaches them — they must render but never resolve.

Generation stays authoritative: the labels and the explicit fields are produced by `tools/acquire_geometry.py`, and `--check` continues to verify token counts against addressable cells.

### D6 — The fits and the spec drop their patch precondition, gated on the inventory

`physical_spec` and `App::physical_chain_and_rack` return `Some` when a patch exists **or** an inventory is configured. With an inventory and no patch, labels and states are empty (no store, no components), the master is `MasterModel::Master`, and the pane title keeps naming the model it drew. Without an inventory and without a patch both still return `None`, so the empty-pane behaviour is unchanged for existing users.

## Risks / Trade-offs

- **An inventoried E4 is a dense dim field** (128 declared LED cells). Accepted: the cells are what the hardware has; a ring presentation is a separate change (non-goal).
- **The rack grows**, so the labels/rack fit shrinks for a large inventory, and a wide rack may need a second `[physical.rack]` row. Accepted: the inventory is the user's own declaration, and the fits already clamp and pan.
- **An inventory typo is silent apart from one warning** (the entry is skipped rather than drawn as a fallback-width faceplate). Chosen deliberately: a mystery 25.4 mm panel is worse than a missing one plus a warning.
- **`cell_for`'s positional fallback remains** for cells with no identity. It is now unreachable for the cells this change normalises, but removing it is a separate risk (it currently keeps a scaled/gated token on a best-effort cell); leaving it means a future unnumbered cell can still resolve to the wrong jack.
- **Docs screenshots**: an inventory changes the master front, so the screenshots that show an inventory-driven rack must be regenerated when `docs/views.md` is updated; without an inventory nothing shifts.

## Migration

- `config.toml` compatibility: `modules` is `#[serde(default)]`, so an existing file loads unchanged and keeps today's behaviour; saving adds the key only where a row already has one.
- No data migration, no store version bump, no change to `labels.toml`/`favourites.toml`.

## Open Questions

- Ring presentation for the E4's 128 LED cells — deferred to its own change.
- Whether the pane title should say `Rack` when no patch is loaded (`Module UI · rack`) — decided during implementation, not load-bearing.
